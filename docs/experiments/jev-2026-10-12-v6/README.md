## 定位过程

1. **固定问题，只改上下文。** 五个运行回归案例加四个控制案例，比较仅身份、共享当前台账、局部文件路径/角色，轮换变体次序，每例每种三次，共 81 次最终请求。恢复共享台账改善所有五例；仅补角色仍不能解决加载后导出。首次共享覆盖中包含有分组名的临时路径，因此该组存在泄漏风险，不能单独作为有效证据。
2. **排除路径泄漏后重复。** 临时目录改为数字编号，模型输入覆盖 scope 固定 `local-project`，重复 81 次。共享上下文的五个回归案例共 15 次运行肯定分数全部 >=0.90；身份输入多数在门槛附近或以下。这表明上下文裁剪是这批回归的重要因素，不能进一步断言一定是文件角色缺失而非证据组织/重复呈现的影响。
3. **固定局部上下文，试明确 criteria。** 另外 81 次只改问题和肯定/否定条件。该候选把加载后导出提升到 0.90，但数组加载降至约 0.88，中文动态加载降至 0.78–0.85。因此拒绝整体重写，实验代码只留在诊断脚本，未用于生产。
4. **采用更小的边界补充。** 对十例再做 90 次对照，比较共享台账、加入用户问题、以及无用户问题且补充两个具体边界。用户提问是非证据输入，对导出案例分数有小幅影响；不是所有案例回归的唯一原因。补充“加载后导出算使用，导出包名不算”和“未实现的未来提案不代表当前消费者缺失”后，导出案例原始分数为 0.94–0.95，未来提案未知消费者分数为 0.08–0.09。最后必须由完整回归确认收益，不能把诊断请求的速度冒充完整审查速度。

最终修改是恢复当前依赖的相关台账、覆盖/缺口与调查历史，移除绝对 scope 和最终用户提问，保留原三正向问题并只补充两个边界句。每条支持记录仍依据其独立原始分数筛选；文档与历史记忆不参与支持度计算。没有新增 LLM 补救，也没有调低阈值。

## 原因判断：事实与假设分开

确定的机制是原始肯定分数下移，加上 0.90 的固定门槛，使更多正确候选变为待审查。分数为什么下移尚未做控制实验，不能直接断言是模型能力下降或全部是阈值错误。

优先假设是上下文裁剪丢失了用途信息。v3 到 v4，运行使用问题文字和完整源码基本不变，但公共状态从包含台账、文件角色线索变为仅依赖/包身份。每条问题里的记录只包含 id、sourceType、summary、content，没有显式 filePath/fileRole；`sourceType: context` 表示证据来源，不表示应用源码用途，摘要 `source/config` 也有歧义。模型仍被要求判断“application source ... as a library”，却不再收到同样明确的角色线索。

另一个假设是问题包含额外的用途与执行条件。“存在已解析的加载”应当独立成立，已加载模块随后导出不应被误当成只导出包名、等待未知消费者。异步加载关系也容易多一步推理。应明确区分导出字符串与导出已加载模块，而不是让一个问题同时证明加载、调用和应用用途。

v4 同时改了第三个问题、公共状态和派生评分，并没有做单因素实验。官方指出模型会按字面理解条件，并建议减少间接推理、保留相关状态；这支持这些候选方向，不能代替本项目的因果验证。[模型局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 下一轮执行顺序

1. **先对照上下文。** 选择五个回归案例，加上普通运行加载、工具链、正确未使用、未知消费者四个控制案例。保持问题、阈值、聚合和文件内容不变，比较当前最小状态、恢复 v3 状态、仅补充明确文件路径/角色三种输入。固定调查顺序，重复测量原始肯定分数与最终类别；这是 Jev 最终决策诊断，不把它的时间当作完整审查耗时。先验证是否缺少相关信息，不直接恢复整份台账。
2. **再单独修改问题。** 在上下文方案固定后，将运行问题明确为“本文件是否存在已解析的目标加载/调用关系”，通过 Noul 的肯定/否定 criteria 明确：已加载后导出算使用、已解析动态 import/require 算使用、仅导出字符串与未知加载器不算已证明使用。工具链用途保留独立判断。避免一边改状态一边改问题，导致再次无法定位收益与代价。[API 支持明确 criteria](https://docs.typesafe.ai/api)
3. **先守住已知回归，再跑 Jev 全集。** 目标恢复运行使用至少 27/30；工具链不低于当前 30/30；未使用不低于当前 10/30；30 个应待审查案例仍正确待审查；错误删除建议与错误确定结论均为零。使用 40 个原案例作回归检查，各预热一次、测量三次，另做六例换序检查；分类指标必须逐组检查。
4. **用新标注材料做独立确认。** 加入模块导出、异步调用、中文/英文混合、文件角色不同、跨文件消费者，以及未知加载器与仅注释的近似反例。覆盖中性包名和含 tool/plugin 的名称。标签在新模型调用前固定，新材料不用于反复试提示。之后才研究是否需要按保留/删除风险分别校准阈值，不为恢复已知案例直接降低删除门槛。

早期诊断按小样本、固定条件比较，日常完整回归只跑 Jev。LLM 历史结果保留作背景；最终独立材料和 Jev 方案稳定后，再显式运行一次新 LLM 对照验证替代可行性。

## 本次交付验证

实验脚本默认不要求 QWEN、不构造 LLM，只有 `--compare-llm` 进入双提供方路径。单独运行的 LLM 摘要、比较项及整体替代验收为 `null`，不把未执行的比较写成通过或失败；新增 `byExpected` 分类统计。

三个脚本回归测试使用假凭证、模拟模型/审查函数和临时目录，不联网，不读取 `.env`，验证默认 Jev、显式对照缺失配置、显式双提供方路径。原始历史报告保持不变。

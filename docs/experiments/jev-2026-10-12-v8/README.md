# Jev v8：消费者边界按记录限定

本轮只调用 `jev-1.13.0`，未调用真实 LLM。默认提供方仍为 LLM，实验只保存在本地分支。调查最多六轮，超时 10 秒，零自动重试；0.90 肯定门槛、0.10 局部否定门槛、覆盖及删除建议检查均未放宽。

## 改动与被拒绝的设计

旧 holdout 的 h05 只有 `export default { plugins: ["tooling-lib"] }`，没有证明加载的消费入口，其原工具链标签有假设；历史标签和结果保持不变。本轮将明确加载插件和导出包名列表分开，也将本地显示文本与导出给未知消费者的数据分开。

第一开发候选改善显示文本，却把没有消费者说明的导出包名判成可删除（局部未知消费者分数 0.08），因此没有采用。第二候选明确保留导出数据的未知消费者边界，在局部开发对照中正确，但附加到所有记录后，完整旧回归退步为 104/120：循环加载被混同工具链、仅含历史/未来注释的源码也增加未知消费者分数。这个通用 v7 候选已被替换，失败结果保留，不用它宣布成功。

最终 v8 复用现有文件角色选择配置/工具链的插件说明，用 AST 区分可执行字符串和注释，只对没有模块加载的真实包名字符串补充显示/导出边界。应用加载、清单命令和仅注释记录沿用 v6 问题。AST 和文件角色只决定提供哪个问题，未直接指定答案、改写原始分数或降低门槛。解析失败仍提供保守边界说明。SDK 输出和融合机制保持不变。

## 仍未过关的三个新边界

- n02：`["tooling", "lib"].join("-")` 后动态 import，三轮中的一轮运行分数为 0.89，低于 0.90，另外两轮正确。旧回归 runtime-4 的一次待审查同样处于 0.89。门槛附近的重复稳定性仍需验证，不能通过向下调整门槛直接宣布解决。
- n13：目标包名保存在旧变量，实际加载的是另一个已知包。三轮未知消费者分数为 0.32–0.37，全部额外待审查。v8 的“存在任何模块加载就使用旧消费者问题”过于粗略，没有围绕目标包梳理字符串到具体消费者的局部关系。下一轮应提供可验证的局部绑定、加载参数及导出/外传关系；无法静态解析的关系仍保留缺口。
- n15：包脚本通过 `node -e` 打印包名文本，没有执行目标命令。三轮工具链分数为 0.13–0.14、未知消费者为 0.14，均额外待审查。应进一步分清 shell 命令、执行参数和仅用于显示的字符串；不能依靠清单字符串中出现包名就判使用。

预先设定的新集目标中，零错误确定结论、零错误删除和六例换序稳定通过；宏 F1 ≥0.95、待审查率 ≤30% 没有通过。仍保留实验功能，不提升默认，也不启动 LLM 对照。上述三个新模式今后可转为开发回归，但下一轮优化后需要另一批未用过的验证材料；本轮首次验证后没有修改生产代码、样本或标签来提高分数。

## 延迟回归

旧集 v8 比历史 v6 的 p50 增加约 46%，p95 增加约 200%，不能说所有指标改善。两轮正式调用均为 360 次，输出 token 都为 26550，输入 token 仅从 370332 增至 371412（约 0.29%）。v8 完整审查减去记录的 API 耗时后，本地工作 p50 为 1 ms、p95 为 2 ms；观测到的延迟增长主要处于 API 请求区间。

这些时间信息不能区分网络等待、服务排队和服务端推理，也不能证明某一因素导致变慢。两轮发生在不同时间，未做同时段交替控制；因此保留全部慢请求并报告回归，不将延迟增长直接归因于新增本地 AST 检查，也不把它排除成异常值。当前新集完整审查 p50 约 1.26 秒、p95 约 2.74 秒，仍不代表大型实际项目体验。
